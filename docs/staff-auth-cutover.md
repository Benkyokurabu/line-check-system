# 職員認証の実装と切替条件

2026-09-05。統合設計の正本を置き換えない実装資料。

## 追加した処理

- 職員コードをサーバー内部で管理済みAuthユーザーへ対応させ、Supabase Authでパスワードを検証する。メールアドレス・トークンを公開プロフィールに含めない。
- 本人検証用クライアントと特権DBクライアントを分離。検証済みトークンから得たユーザーID・セッションIDだけをDBへ渡す。
- DBは職員の有効状態、Authセッションの存在、パスワード変更、絶対期限・無操作期限、役割と個別権限を再確認する。設定値と権限は変更可能。初期権限をSQL再適用で復活させない。
- Secure / HttpOnly / SameSite=Strict / __Host- Cookie、変更要求のOrigin確認、JSONサイズ上限、認証応答のキャッシュ禁止を実装。
- DELETE `/api/staff/session` は期限切れのアクセス情報を更新してから対象セッションだけを解除する。接続失敗は解除成功と報告しない。失敗時も端末側Cookieは消すため、サーバー解除を確認できなかった場合は管理側での失効確認が必要。
- POST `/api/staff/study-room/transition` は職員IDの自己申告を無視し、DBの職員権限確認と予約承認・却下・取消を同一トランザクションで行う。
- `/staff/self-study-room` にログイン、対象日・状態別の申請一覧、承認・却下・取消の確認画面、通信結果不明時の同一操作IDでの再確認、ログアウトを接続した。表示状態の選択は職員別・端末別に記憶し、生徒情報やパスワードはブラウザ保存しない。共通の端末間設定同期は未接続。
- `staff_study_room_read_20260905.sql` は閲覧権限を確認して1日分を50件ずつ返す。LINE識別情報や内部の操作記録は一覧に含めない。ページ移動中に申請が増減した場合は先頭から再読込みする。
- `staff_study_room_intake_20260905.sql` と POST `/api/staff/study-room/intake` に職員代理受付を追加した（DB未適用）。`study_room.submit` 権限、連絡方法、理由を必須とし、申請と受付根拠を同一トランザクションで保存する。LINEの送信者と入力職員を混同せず、登録後は承認待ち・座席未確保とする。申請IDの再送で根拠が変わった場合も拒否する。
- 代理受付追加後は職員テスト33件、全体140件がローカルで成功（独立PostgreSQL専用2件はスキップ）。関連lint・型チェック成功。ローカルビルドは `.next-staff-test/static` もOneDriveのReadOnly/ReparsePointになり、権限制限外での再実行でもEPERM。既存出力を削除せず、GitHub Actionsのクリーン環境でビルドとブラウザ試験を確認する。

## 検証の限界

- ローカル検証: 職員認証25件成功、`npm test` 全体132件成功・独立PostgreSQL専用2件スキップ、型チェック・関連lint・本番ビルド成功。ビルド開始時にPowerShell側の例外表示があったが、同じ実行ハンドルでビルド完了・終了コード0まで確認した。
- コアのテストはAuth応答を差し替えた検証用。DBテストもメモリー内の隔離PostgreSQLと簡略Authテーブルを使用し、実在アカウント・本番データ・LINE送信を扱わない。
- パスワード照合そのもの、実サービスの更新・失効、ブラウザCookieや画面操作、ネットワーク断後の復旧を実証したものではない。
- [Supabaseのセッション仕様](https://supabase.com/docs/guides/auth/sessions)に従い、JWT検証だけでなくAuthセッション存在も確認する。[管理APIのログアウト](https://supabase.com/docs/reference/javascript/auth-admin-signout)を使用する。Auth内部テーブルへの依存は実環境のスキーマと権限を適用前に確認する。

## 利用開始前に残る条件

1. 職員画面の基本接続と、生徒検索・空席表示・代理受付・受付根拠の閲覧画面は追加済み（初期無効・SQL未適用）。受付根拠は閲覧権限のある職員の一覧にだけ含め、LINE識別子やAuth情報は返さない。受付担当者名は現在の職員登録名であり受付当時の名称スナップショットではないことを画面に明示する。来退室確認・設定画面と共通設定同期、実セッションの期限切れ・共有端末の離席時ロックを含む実環境の受入試験は残る。
2. 全対象職員のアカウント管理、初期配布、パスワード再設定、退職・紛失時の失効、変更監査を整備する。アカウント作成・案内送信は許可された段階で行う。
3. 現行の認証なし予約・管理APIを安全に切り替え、読み取りを含めた情報漏えい・迂回経路を閉じる。新経路だけの検証で完了にしない。
4. 実Authサービスと隔離された試験用アカウントでログイン・更新・失効・同時操作を確認する。共有端末、複数タブ、通信障害、Origin・Cookieのブラウザ実測も必要。
5. 適用前バックアップと復元手順を確認し、予約ワークフローSQL、職員認証SQL、職員申請一覧SQL、職員代理受付SQL、`staff_study_room_options_20260905.sql` の順に適用する。SQLは機能を有効にせず、現在は本番未適用。
6. サーバーの `STAFF_AUTH_ENABLED=true` と、実際のHTTPS配信元を指定した `STAFF_AUTH_ORIGIN`、DB側の有効設定を揃える。設定変更は利用開始の許可と準備完了後。秘密値をチャットに転記しない。

本機能の追加は既存APIの認証対応完了でも、塾全体の統合完了でもない。

## 来室・退室確認（初期無効・本番未適用）

- `staff_study_room_visits_20260905.sql` と POST `/api/staff/study-room/visits` を追加。既存の職員認証・Origin検証・初期無効設定を共用し、`study_room.visit` 権限を毎回確認する。SQLは職員認証・予約ワークフローの後に適用するが、現時点では本番未適用。
- 実利用開始・終了、終了後の移動先（授業・帰宅・その他）、確認職員・確認時刻を予約とは別に保持する。日本時間の利用日、不正・未来時刻、終了と開始の前後関係を検証する。初回記録は確定済み予約に限定する。
- 通常の退室追記を除く訂正は理由を必須とし、変更前後を削除不可の履歴へ保存する。誤った記録は履歴を残して未確認へ訂正できる。予約取消後も既存の実績訂正は可能。
- 操作IDの再送と版番号で二重記録・上書き競合を防ぎ、履歴保存に失敗したら実績変更も取り消す。退室しても席の予約枠・授業出席・塾の打刻・帰宅通知を変更しない。
- 職員一覧に現在の来室・退室実績、移動先、最終確認日時・職員名を接続した。`study_room.visit` 権限がある職員は入力画面から時刻・移動先・訂正理由を確認して保存できる。予約時刻を実績の初期値にはせず、「現在時刻を入れる」は明示操作とする。時刻は日本時間に固定する。
- 記録編集・結果不明の間は他の承認・代理受付・一覧操作を抑止し、同じ操作IDで結果を再確認する。期限切れ・ログアウトで編集内容を消去し、記録の版競合時は一覧を再取得する。新しい一覧SQLは来退室テーブル作成後に利用する。
- 訂正履歴の閲覧を追加した。`staff_study_room_visit_history_20260905.sql` は来退室SQLの後に適用する（本番未適用）。職員の閲覧権限を毎回確認し、変更前後の開始・終了・移動先、記録職員、日時、理由だけを返す。内部操作ID・Auth情報は返さない。新しい順に20件ずつ、版番号を基準に古い履歴を取得する。
- 画面で変更前後を項目別に比較できる。履歴はブラウザの永続保存へ書かず、取得エラー時は表示済み履歴も消去、期限切れ・ログアウト時は生徒情報ごと消去する。
- 複数回の出入り、柔軟な移動先設定、当日受付から利用開始までの一連操作は未接続。今回の入力・履歴接続だけを来室・退室機能全体の完成とは扱わない。
