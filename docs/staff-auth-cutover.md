# 職員認証の実装と切替条件

2026-09-05。統合設計の正本を置き換えない実装資料。

## 追加した処理

- 職員コードをサーバー内部で管理済みAuthユーザーへ対応させ、Supabase Authでパスワードを検証する。メールアドレス・トークンを公開プロフィールに含めない。
- 本人検証用クライアントと特権DBクライアントを分離。検証済みトークンから得たユーザーID・セッションIDだけをDBへ渡す。
- DBは職員の有効状態、Authセッションの存在、パスワード変更、絶対期限・無操作期限、役割と個別権限を再確認する。設定値と権限は変更可能。初期権限をSQL再適用で復活させない。
- Secure / HttpOnly / SameSite=Strict / __Host- Cookie、変更要求のOrigin確認、JSONサイズ上限、認証応答のキャッシュ禁止を実装。
- DELETE `/api/staff/session` は期限切れのアクセス情報を更新してから対象セッションだけを解除する。接続失敗は解除成功と報告しない。失敗時も端末側Cookieは消すため、サーバー解除を確認できなかった場合は管理側での失効確認が必要。
- POST `/api/staff/study-room/transition` は職員IDの自己申告を無視し、DBの職員権限確認と予約承認・却下・取消を同一トランザクションで行う。

## 検証の限界

- ローカル検証: 職員認証25件成功、`npm test` 全体132件成功・独立PostgreSQL専用2件スキップ、型チェック・関連lint・本番ビルド成功。ビルド開始時にPowerShell側の例外表示があったが、同じ実行ハンドルでビルド完了・終了コード0まで確認した。
- コアのテストはAuth応答を差し替えた検証用。DBテストもメモリー内の隔離PostgreSQLと簡略Authテーブルを使用し、実在アカウント・本番データ・LINE送信を扱わない。
- パスワード照合そのもの、実サービスの更新・失効、ブラウザCookieや画面操作、ネットワーク断後の復旧を実証したものではない。
- [Supabaseのセッション仕様](https://supabase.com/docs/guides/auth/sessions)に従い、JWT検証だけでなくAuthセッション存在も確認する。[管理APIのログアウト](https://supabase.com/docs/reference/javascript/auth-admin-signout)を使用する。Auth内部テーブルへの依存は実環境のスキーマと権限を適用前に確認する。

## 利用開始前に残る条件

1. 職員ログイン画面、ログアウト・期限切れ表示、承認一覧・代理受付画面を接続する。
2. 全対象職員のアカウント管理、初期配布、パスワード再設定、退職・紛失時の失効、変更監査を整備する。アカウント作成・案内送信は許可された段階で行う。
3. 現行の認証なし予約・管理APIを安全に切り替え、読み取りを含めた情報漏えい・迂回経路を閉じる。新経路だけの検証で完了にしない。
4. 実Authサービスと隔離された試験用アカウントでログイン・更新・失効・同時操作を確認する。共有端末、複数タブ、通信障害、Origin・Cookieのブラウザ実測も必要。
5. 適用前バックアップと復元手順を確認し、予約ワークフローSQL、職員認証SQLの順に適用する。SQLは初期無効で、現在は本番未適用。
6. サーバーの `STAFF_AUTH_ENABLED=true` と、実際のHTTPS配信元を指定した `STAFF_AUTH_ORIGIN`、DB側の有効設定を揃える。設定変更は利用開始の許可と準備完了後。秘密値をチャットに転記しない。

本機能の追加は既存APIの認証対応完了でも、塾全体の統合完了でもない。
