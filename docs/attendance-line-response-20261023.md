# 遅刻・欠席のLINE更新が待機し続ける場合の対応

2026年10月23日。既存の一覧・入力・確認・返信操作を維持して、更新ボタン直下に現在の状況と結果を表示する。

- 確認結果を待つ段階と、確認後に一覧・処理状況を更新する段階を区別する。
- 読み取りは15秒、LINE確認は45秒を上限に、本文の受信も含めて応答を待つ。
- 時間切れでも画面内の既存連絡を消さない。確認処理の結果は不明であり、サーバー側で続いている場合があることを示す。失敗や未確認を0件・全件処理済みとは扱わない。
- 一覧更新だけが失敗した場合は、受け取れた確認結果を残し、ボタンを再び操作できる状態へ戻す。

本番調査ではアプリのバージョンAPIは応答したが、遅刻・欠席の処理状況API、保存先Data API、認証サービスの応答待ちを確認した。直接DB接続では保存済みLINEと解析待機0件を確認できた時点がある一方、接続・単純な読み取りにも遅延があった。保存先の公式障害情報は関連する可能性があるが、この事象との因果関係が確定したとは扱わない。長時間ロックによる閉塞は調査時点で確認していない。

画面の待機保護の配信と、外部サービスを含む取得経路の復旧は別に検証する。送信・業務データの修正・同期ロックの解除は行っていない。

関連lint、型チェックを含む通常本番build、およびブラウザ12件が成功した。追加した試験は確認APIの無応答と処理状況更新の無応答を再現し、結果説明・ボタンの再操作・確認結果の保持・説明文がボタン直下にあることを検証する。既存の選択・非表示・復元も検証した。

次の依頼は、復旧作業の後で勉たん全体へ状況説明を広げ、失敗時の実際の情報をAIが分析した説明に「AIによる分析」と明記すること。今回の画面説明は処理状態に基づく表示で、生成AIの診断を実装済みとはしない。
