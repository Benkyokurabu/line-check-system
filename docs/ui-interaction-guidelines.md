# 操作結果と一覧表示の共通方針

確認日：2026年10月22日。勉たんに限らず、今後の画面作成・変更時に適用する。既存の正常な操作を維持し、変更する画面と業務に必要な範囲へ反映する。

## 追加提案と動作確認を明示する

- ユーザーが指定していない追加UIは「提案」と示し、何のためにあるかを各操作の近くに短く説明する。理由があることを採用済みと解釈しない。
- 架空データの改訂・再通知等を試す操作は、通常業務から分けた「動作確認用」の欄にまとめ、実際に変更・送信するかを明示する。
- 個人ブックマークの保存と、原文を記入する保存のように、同じ語で異なる操作を示さない。目的が分かる名前にする。

## 結果を確認できる状態を保つ

- 保存・読了・採用・保留などを実行した直後に、対象行や結果説明を突然消さない。何を、どう処理したかを対象の近くに残す。
- 成功メッセージを短いタイマーや次の無関係な操作だけで消さない。別の結果への更新、明示的に閉じる操作、意図した画面移動など、利用者が理解できる契機で切り替える。
- 実行中・成功・一部成功・失敗・未実行を区別する。遅い通信でも対象と進捗を表示し、完了前に成功済みの見た目へ変えない。
- 失敗時は入力・選択・対象行を保ち、どこまで保存されたか、再試行する対象は何かを分かるようにする。一括処理では件数と対象ごとの結果を確認できるようにする。

## 選択と実行を区別する

- 複数項目をまとめて処理する一覧では、チェックボックスは対象の選択に使い、対象件数と実行内容を示したボタンで明示的に実行する。
- 「読んだ」「確認した」という業務上の記録と、「非表示」「削除」という表示・データの操作を混同させない。両方が必要な場合は別の操作として分かる名称にする。
- チェックした瞬間に行が消える設計は避ける。読了後に未読一覧から外す必要がある業務でも、まず結果を確認できる状態を保ち、明示的な一覧更新や非表示操作など、意図が分かる形で切り替える。
- 単独の明確な操作をすべてチェックボックスに置き換えない。保存ボタンを押すたびに確認ダイアログを追加しない。確認は取り消しが難しい操作や対象範囲が誤解されやすい場面に絞る。

## 一覧の見通しと詳細

- 一覧は短い行を基本とし、名称・状態・必要な日付・操作結果を見渡せるようにする。長い本文・根拠・理由・履歴は行のクリックや明示的な詳細展開から確認する。
- 詳細の開閉自体を読了・採用・保存とみなさない。キーボードでも詳細を開閉でき、操作名から結果を予測できるようにする。
- 判断済み・非表示にした項目を履歴から見直せる導線を用意する。業務上許される場合は取り消しや判断変更を用意し、できない場合は履歴と訂正方法を示す。

## 操作位置を維持する

- 保存や一覧更新で、利用者が見ていた位置・開いていた詳細・入力中の理由・キーボードのフォーカスを不用意に失わせない。安定したIDで行を保持し、画面の先頭へ自動移動しない。
- ボタンの連打で処理が重複しないようにしつつ、実行中の表示と結果を確認できるようにする。通信エラーや一括処理でも同じ方針を適用する。

新規画面や既存画面の変更を確認するときは、通常時に加えて、通信待ち・失敗・部分成功・同じ行への再操作・一覧更新後の状態を必要な範囲で確認する。
