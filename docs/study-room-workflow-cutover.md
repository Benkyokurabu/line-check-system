# 自習室の承認処理：実装と切替条件

更新日: 2026-09-05

設計の正本は `自習室予約システム/統合システム設計メモ.md`。本書は実装・検証・切替の補助資料。

## 現在の成果物

`supabase/self_study_room_workflow_20260905.sql` は、本番には未適用のマイグレーション。既存の自習室SQLとLINEの職員確認状態のマイグレーションを前提とする。新規作成時の `enabled` は false。再実行しても有効・無効を勝手に切り替えない。

- 申請時は `pending`。申請者、対象生徒、続柄のスナップショット、受付経路、日本時間の通常／当日区分を記録する。
- 空席の正本は従来の `study_room_reservations` の有効行のみ。申請テーブルは希望内容・状態・履歴であり、別の予約在庫ではない。
- 申請時と承認時に、空席、同一生徒の同時間帯重複、日別上限、使用不可枠を確認。申請だけでは席を確保しないため、他の生徒の承認により承認できなくなった申請は承認待ちに残る。同一生徒の重複した承認待ち申請も拒否する。
- 承認で選択した全枠を一括確保。承認者・日時・版履歴・通知予定の記録まで一つのトランザクションにする。途中失敗時は全体をロールバックする。
- 取消では元の申請・承認者・予約行を残し、枠を解放する。却下には理由が必要。古い画面の版による変更を拒否する。
- 操作IDの再送で同じ申請や履歴を増やさない。同じIDで内容を変更した要求は拒否。再送の応答は申請の**現在の状態**を返し、後から取り消した申請を復活させない。
- 通知予定は送信結果と別に保存。送信失敗だけで席を解放しない。宛先決定・送信・再送処理は未接続で、このSQLからLINEを送信しない。
- 本人・保護者の操作では確認済みのLINE紐づけをDBでも再確認。職員はサーバー側で個人認証と操作権限を確認してから呼ぶ前提。
- 一般のブラウザ向けDBロールは申請・履歴を直接読めず、RPCも呼べない。サービスロールにも監査行の更新・削除は許可しない。
- 有効化後は旧APIによる在庫の直接作成・取消を拒否。新方式で作った予約は無効化後も旧APIで変更できない。履歴を削除する復旧方法は採用しない。

## 検証

`npm run test:reservation-db` は、通常は [PGliteのメモリ内Postgres](https://pglite.dev/docs/) だけを使用する。環境ファイルを読み込まず、本番DBには接続しない。この方式は単一接続なので、これだけで同時接続の安全性を確認したとは扱わない。

GitHub Actions の `study-room-postgres` は、廃棄可能なPostgreSQL 16サービスで同じテストと複数接続の競合テストを実行する。テスト専用URLを指定する場合も、localhostかループバックかつDB名 `study_room_workflow_test` のみ許可する。これは検証用であり、本番接続先を指定しない。

検証範囲は、無効時の拒否、既存データを残した再適用、本人・保護者・兄弟の権限、当日申請、再送、重複、承認、複数枠の原子性、上限・休室の再確認、取消・却下・履歴、通知予定保存失敗時の全体ロールバック、直接DB権限、旧経路による迂回防止。複数接続では同一席の承認競合と一人当たり日別上限の競合を検証する。

2026-09-05のローカルDBテストは22件成功、実PostgreSQL用の2件はスキップ。型チェック・関連lintも成功。実PostgreSQLとクリーンなビルドの結果はCIで別途確認する。

同日の `npm audit` は既存パッケージにhigh 8件を報告（next、xlsx等）。追加したPGliteは対象に含まれず、ロックファイルの変更もPGliteの追加のみ。今回、無関係な依存関係の一括更新は行っていない。利用開始前のセキュリティ確認項目として残す。

## 本番切替の前に必要な作業

以下は未完了。SQLのテスト成功やコードの公開だけをもって利用開始しない。

1. LINE本人認証と、職員コード・個人パスワード認証／権限を実装する。RPCに渡す申請者・承認者をクライアント入力から採用しない。特に `actor_kind = staff` は認証済みという証明ではない。
2. 既存の予約・取消・管理APIを認証付き経路へ切り替え、他の生徒の氏名・学籍番号・申請内容を空席情報に混ぜない。申請一覧・承認・却下・取消・再読込・競合表示を画面へ接続する。
3. 利用対象の在籍状態、不変の生徒IDへの接続、開校・休校、施設・時間枠・終了済み枠・日別例外を実装する。このSQLは既存の本校10席・90分4枠の形式を引き継いでおり、全体の可変設定完成版ではない。
4. 通知宛先の確定・二重送信防止・送信監査・再送を実装する。取消・却下の通知可否なども既決の設定方針に合わせる。
5. 設定画面、権限、変更者・変更前後・適用日の監査を用意する。DBの有効フラグを直接変更する方法を通常の設定UIの代わりにしない。
6. 本番DBの構造・バックアップ・既存予約件数を読み取り確認し、DB変更の承認後に適用する。既存の確定予約を勝手に承認待ちに変えない。旧予約を新しい履歴管理へ引き継ぐ手順と件数照合が必要。
7. 画面・APIの切替確認後に有効化する。旧画面はエラーになるため、旧URL・メニューを放置しない。切戻し時は新規受付を停止し、承認済み枠・取消履歴・未送信通知を残したまま職員対応する。

来退室確認、入退室管理（初期無効）、面談予約など、正本で決定済みの残りの統合範囲も引き続き実装対象。
