保存場所・権限・情報の鮮度
  • 処理台帳・索引・キャッシュは処理用PCのローカルSSD。SQLiteの稼働ファイルをNASやOneDrive同期フォルダへ置かない。
  • 面談資料は従来の「98面談資料」配下へ、不変の版と表紙HTMLを保存。一般のNAS原本は読み取り専用を維持する。
  • 運用台帳の退避用共有フォルダは新たな保管先の候補。現在の面談資料保存許可を他領域へ広げず、導入時に専用領域とACLを設定する。
  • 塾内画面はLAN内のHTTPS。インターネットへポートを直接公開しない。塾外では既存Web画面と事前取得済みの端末下書きを利用する。
  • 認証の正本は既存の職員認証。ローカルに職員パスワードを複製しない。認証済み職員・端末・許可された操作へ限定した期限付き権限をオンライン時に発行し、塾内で署名と期限を検証する。期限初期案は最大8時間。失効確認を要求する重要操作はオフラインで実行しない。
  • 期限後は個人情報を新規表示しない。未送信原文は暗号化したまま保護し、再認証してから再開する。ログアウト時は閲覧用コピーと未反映原文を分け、未反映原文を黙って削除しない。
  • 端末・サーバーのディスク暗号化、職員別アクセス制限、バックアップ暗号化、端末故障時の復旧鍵の別保管を導入条件にする。サービス秘密値はブラウザや公開JSONへ入れない。
  • 公開予定の保存版は初期案24時間、録画の公開許可版は初期案15分で再確認。期限切れ録画はリンクを表示しない。今回の193件には別途承認された10月27日13:53までの緊急ルールを維持し、新しい既定値で勝手に変更しない。
  • 録画の期限・非公開は画面からのリンク表示を制御する。既に渡ったZoom URL自体を無効化するには、Zoom側の設定変更が別途必要。
  • 長期保存する確定資料と、一時的な読み取り用キャッシュの期限は別管理。期限切れを理由に確定資料や監査履歴を削除しない。

塾内APIと外部反映の契約
  • POST /ops/v1/commands：操作UUID・案件・基準版・本文ハッシュ・職員権限を検証し、台帳へのコミット後に「受付済み」を返す。同一UUID・同一本文は既存結果、異なる本文は409。
  • GET /ops/v1/commands/{id}：端末保存・受付・退避・反映先別結果を返す。自分が扱える案件だけを取得。
  • POST /ops/v1/jobs：資料作成等を登録。クラウドから同じ依頼を受けても一意キーで重複防止。
  • GET /ops/v1/artifacts/{id}：現在の権限を確認して完成版を取得。未検証の一時ファイルは返さない。
  • GET /ops/v1/status：最終巡回・未処理数・失敗分類・最終退避を表示。一般公開の健康確認には個人名を含めない。
  • 反映直前に正本の版を確認。Notionなどに原子的な版指定更新がない場合、読み戻しだけでは競合を完全防止できない。同期対象の管理領域に限定し、元の段落・添付を保持。変更が競合し得る処理は人の確認へ回す。
  • Notion新規作成の応答が不明な場合は、操作IDと対応表で作成済みを探す。一意に確認できなければ再作成しない。表示用備考へ内部IDを追加しない。
  • LINE等は既存送信処理を共用し、宛先・本文・操作UUIDを保存。既存処理の停止や成功確認前に別経路の送信へ切り替えない。LINEのretry keyは対応API・期限・同一内容の条件内でのみ利用し、結果不明時の自動再送停止という現行運用を維持する。

Excel依存部分の扱いと、実装時の構成

PDFの結合・原本読み取り・OCR索引は既存Python処理を再利用し、巡回・受付・保存検証をクラウドDBから分離します。受付と巡回はOSのサービスとして動かせる部分に分けます。

現行の指導簿PDF出力はExcel COMを利用し、Windowsログインと対話用ユーザープロファイルが必要です。OfficeをSYSTEMのタスクや無人サービスへそのまま移す構成は採用しません。移行中は既存の職員操作環境で変換し、変換不可時はその依頼だけを保留します。

完全な無人化は、指導簿の構造化値から帳票を描画する変換器へ置換し、全パターンの数式結果・表示・改ページをExcel出力と照合してから行います。対話型Excelを残す段階を、無人運用完成とは扱いません。

故障しても、二重処理を起こさず戻す

主担当PCが止まった場合

  1. 新しい外部更新を停止。職員端末は下書きと取得済み情報を保持する。
  2. 旧主担当PCを停止または通信から隔離し、後から勝手に復帰しないことを確認。接続できないだけでは予備を自動昇格しない。
  3. 予備PCへ検証済みバックアップを復元。復旧鍵を別の保管先から利用し、前のPCにしかない鍵へ依存しない。
  4. 新しい担当世代を発行。最後の退避以降に送信が始まった可能性のある反映は「結果不明」にする。
  5. 端末に残る同じ操作UUIDを再受付し、先方の受付ID・内容と照合する。成功済みは再実行しない。
  6. 資料作成の読取処理から再開し、外部更新は確認後に再開する。旧PCの復帰時は予備として再登録する。

一度に切り替えず、業務ごとに導入する

第1段階 / 閲覧と資料作成

既存の処理を塾内で再利用する

予定表の確認済み出力とNASの面談資料を先に整備。塾内の処理台帳・定時巡回を追加し、Notionからの取得とPDF作成をクラウドDBなしで動かす。既存原本と画面を維持します。

今日の速度修正はこの一部。新しい台帳・定期実行・Excel代替は未実装。

第2段階 / 入力保持

工藤先生の案件から試す

案件別の端末下書き、塾内受付、退避、反映先別の結果を追加。既存の面談後入力の原文・版・宛先履歴を引き継ぎ、正式運用前の制限を維持して試用します。

第3段階 / 運用継続

予備機・監視・復元を確認する

旧主担当を止めて予備へ復元し、未処理が残ることと重複送信しないことを検証。Excel依存を解消できた処理から無人化し、担当範囲を広げます。

本番へ切り替える合格条件
  1. DB・Notion・NAS・インターネット・主担当PCを個別に停止して、想定表どおりの表示と保留になる。
  2. 同じ操作の連打・再起動・端末再送・予備復元で、二重登録・二重送信が起きない。
  3. 書込途中の強制終了後も、原文・実行中・結果不明を識別し、未検証の資料を表紙から開かない。
  4. 本人違い・同姓同名・同日複数面談・最新回答の曖昧さ・原本変更で停止し、旧資料を保護する。
  5. HTML改行形式・日本語ファイル名・NASコピー・全PDFページを確認。キャッシュ期限・権限切れ・他職員の原文アクセスを検証する。
  6. 既存のクラウド実行と新しい塾内実行を同じ業務で同時に有効化しない。業務ごとの実行担当を切り替え、復帰手順も試す。
  7. 外部送信をしない隔離試験 → 工藤先生の試用 → 運用確認の順。既存の「正式には試してからリリース」を維持する。

現在の設計では、正本DBの障害そのものを無くすとは約束しません。まず日常の閲覧・資料作成・原文保持を続け、確定処理と外部送信を正しく再開できる範囲を広げます。クラウドDBを塾内へ全面移行するかは、この構成の運用結果を見て別に判断します。

確認した既存構成と根拠

  • 統合設計の正本：統合システム設計メモ。正本を一つに保つ、履歴を残す、業務ごとに試用する方針を継承。
  • 既存実装：local_helper/helper.py、remote_worker.py、daily_auto.py、/api/material-worker。現在の実行依頼・lease・保存前確認は共有DBに依存する。
  • 現行の面談資料は主担当・予備PC、既存NAS、Excelを利用。毎日自動作成の初期値は無効。今回の設計で有効化していない。
  • NAS指定の業務録画一覧を確認し、10月17日の保存済み業務記録と10月19～21日の訂正を照合。追加の10月23日録画は内容未確認のため、今回の決定根拠に含めていない。

技術上の根拠

  • SQLite WAL：同一ホスト内の運用を前提とし、共有NASへ稼働DBを置かない。
  • SQLite Backup API：整合性のある退避と復元試験を行う。
  • Service WorkerとIndexedDB：画面・取得済みデータ・案件別下書きの端末保持に利用。
  • MicrosoftのOffice自動化に関する注意事項：対話型Excelを無人サービスへそのまま移さない。
  • LINEの再試行仕様：対応API・同じ宛先と本文・キーの期限を確認。受付と配信を区別し、現行の結果不明時の自動再送停止を維持。

未確認事項：常時稼働させる物理PCの割当、校舎間の到達性、NASの退避領域と権限、別系統の保管先、実機の処理容量。設計の既定案として整理し、現時点の本番設定とは扱わない。
