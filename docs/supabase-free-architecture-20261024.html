NASと別系統保管

原資料・完成した資料・添付ファイルを管理。DBはPC内SSDへ置き、整合性のあるバックアップを別の保管先へ退避する。

認証とDBアクセスの実装方針
  • 現在の職員認証はSupabase Authのパスワード照合・getUser・refreshSession等を利用しているため、接続先の変更だけでは動かない。ログイン入口を維持し、内部を塾内認証の実装へ置き換える。
  • 職員IDと権限の対応表を移行。パスワードのハッシュが互換で移行可能か検証し、できない場合は本人確認済みの再設定手順を使う。平文パスワードを取り出したり、チャットで入力させたりしない。
  • 新しい認証は検証済みの標準ライブラリで実装。適切なパスワードハッシュ、短いアクセストークン、回転・失効できる更新トークン、HttpOnly・Secure Cookie、CSRF対策、試行制限、監査を持つ。端末・権限の登録範囲を広げない。
  • 移行時に古いSupabaseセッションを有効な塾内セッションとして流用しない。切替時に再ログインし、無効な職員・古い権限で入れないことを確認する。
  • SQLはAPI経由のパラメーター化された処理とし、ブラウザからDBへ直接接続しない。運用アカウントをDB所有者・スーパーユーザーにせず、権限・RLS相当の条件を試験する。
  • auth.uid()、認証セッション、request claims、拡張機能、DB role等に依存するSQLを分類。既存の権限検証を外してRPCを動かす変更はしない。
  • データアクセスをリポジトリー層へ集約し、業務別にテスト。Supabase SDKの名前だけを残した大規模な疑似クライアントや、一括文字列置換は採用しない。

塾外の利用・LINE Webhookをどう接続するか

塾内は同一のHTTPSドメインで画面とAPIを提供し、DBはLAN内またはローカルホストに限定します。DBの5432番ポートをインターネットへ公開しません。

塾外の職員用はVPN等の管理された経路を利用する案です。生徒向けの動的受付とLINE Webhook等は公開HTTPSの入口が必要なため、回線・ルーター・管理可能なドメイン・証明書を確認し、リバースプロキシから許可したAPIだけへ転送します。TLS・認証・署名検証・負荷制限を行い、管理APIを同じ公開範囲へ入れません。

既存の vercel.app のURLを塾内PCのIPへ直接付け替えることはできません。管理可能なドメインとURL移行、CookieのOrigin、LINE/ZoomのWebhook・callback・許可Originの変更を導入計画へ含めます。回線が外部着信を許可しない場合は、公開入口の中継サービスが追加の依存先になります。通信の入口が確定するまで、生徒・保護者の本番受付を切り替えません。

公開入口を外部に置く場合でも、業務DB・認証をその中継先へ再び依存させません。障害中は塾内の業務と端末下書きを継続し、塾外からの新規接続は停止または待機として扱います。

主担当1台＋予備PCを事前に用意する

DBはPostgreSQLの継続複製を使う案です。予備は通常読取専用、業務ワーカーは無効。DBデータは各PCのSSDに保存し、NAS上の同じDBファイルを2台で開きません。

  1. 主担当と予備へ同じアプリ版・互換DB版・必要な設定を設置。秘密値はPC別に保護し、旧資料作成用のworker設定をそのまま交換しない。
  2. 予備へDB変更を継続送信し、受信・適用位置と遅れ、残り容量を監視。初期案は非同期複製とし、通常の保存が予備1台の停止だけで全停止しないようにする。
  3. 書込・送信の実行主体は主担当だけ。担当世代と操作UUIDを用い、切替前に旧主担当の停止・隔離を確認する。
  4. 主担当の障害時は、複製の到達位置を確認して予備を昇格。安全な接続名・公開入口を切替し、未確認の外部処理を照合してからワーカーを再開する。
  5. 旧PCが戻ったら元主担当のまま再開せず、現在の主担当から予備として再構築する。

非同期複製には未到達データが失われる余地があります。遅れを監視し、端末原文と操作控え、別系統バックアップで補います。「必ず損失ゼロ」や「完全自動切替」とは扱いません。重要な確定処理で同期複製が必要かは、応答時間と予備停止時の扱いを実測して設定します。

本番を止めず、元データを保護して移す

1 / 完全な棚卸しと取得

DB・認証・ファイルを別々に確認する

本番テーブル・件数・制約・インデックス・関数・トリガー・RLS・拡張・時刻設定を取得。認証のID・権限・ハッシュ形式・無効状態と、Storageの全オブジェクト一覧・本体・ハッシュを取得します。

SupabaseのDBバックアップにはStorageのファイル本体は含まれないため、別途転送して照合します。ローカルに残る一部JSONやNASの資料だけで、全データがあるとは判断しません。現在、移行用の完全な取得と復元検証は未完了です。

2 / 外部送信しない複製環境

データ層・認証・ファイル配信を置換する

塾内DBへ復元し、Supabase固有の認証・storage・role・拡張依存を置換。LINE送信・Zoom作成・Notion更新・公開出力は無効にした隔離環境で検証します。

3 / 対象を限定した試用

ログインから業務まで一通り確認する

権限・ID・件数・参照関係・履歴・面談記録・一括反映・資料・LINE添付・予約競合を照合。Supabase通信を遮断した状態で職員ログイン、入力、保存、資料表示、定時受付が動くことを確認します。既存の工藤限定試用と正式公開前の扱いを守ります。

4 / 本番切替

書込先を同時に二つ持たない

旧側の書込と定時処理を止め、差分を最終取得して照合。未完了・結果不明の処理を一覧にし、接続先・認証・URLを新側へ切替します。旧側へ新しい書込を流さないようにし、読み取り用の復旧資料として保持します。

5 / 復帰試験と撤去

新側で書いた後は、その分も戻す

切替後に新しい入力がある場合、旧DBへ接続を戻すだけのロールバックはしません。新規の操作・ファイル・外部送信結果を取り出し、差分反映と重複防止を確認してから復帰します。安定運用と復元試験を終えてからSupabaseの契約・プロジェクトの扱いを決めます。今は停止・削除しません。

DBが無応答のまま、データを失わず即日で全面移行できるとは断定できません。旧DBへのアクセス回復、または完全なバックアップからの復元確認が移行の前提です。今日の予定表と面談資料は引き続き使える経路を維持します。

切替の合格条件
  1. 新環境の実行時通信・環境変数・SDK依存にSupabaseの必須接続がない。別の古いクライアントが残っていない。
  2. 認証・役割・無効職員・セッション更新・ログアウト・CSRF・他人の記録へのアクセス制限が元と同等以上。
  3. 全テーブル・ファイルの件数と対応ID、本文、履歴、添付、NULL、日時を照合。サンプル表示だけで移行完了としない。
  4. RPC・トリガー・排他・一意制約・RLS相当を検証し、同時受付でも予約や業務を二重確定しない。
  5. 主担当・予備・NAS・回線を個別停止し、保存控えと結果不明を失わず再開できる。
  6. 公開URL・Webhook・Callback・Origin・ファイル権限・公開制限・保存期限を実際の経路で確認。
  7. 移行中に外部送信を発生させず、切替後の成功済み操作が再実行されない。

常時ONのPCがない場合：曜日で処理を分担する

資料作成・OCR・原本の取込みは、曜日別の優先PCと、実際に稼働しているPCの両方で担当を決められます。曜日だけで固定せず、当番が停止中なら次の稼働PCを候補にします。全PC停止中の未処理は、次の起動時に期限を再確認して再開します。

構成できること停止時間の扱い
処理PCだけ曜日交代Web・認証・DBは固定の常時稼働環境へ置き、資料作成等を塾のPCで分担。Supabaseを使わない構成も可能資料作成は次の稼働PCを待つ。Web受付とDB保存は継続。塾内に固定機を置けないなら、別の常時稼働環境が必要
DB・認証も曜日交代営業時間中にいずれか1台を主担当にし、塾内ですべて処理全PC停止中は新規ログイン・共有DB保存・動的受付が停止。次の担当へDBを引き継いで再開
既存の生徒向け静的配信公開済みの予定・リンクを既存公開先から閲覧塾のPCが止まっていても閲覧可能。新しい更新はPC起動後。オンライン動画にはZoom等への接続が必要

曜日でファイルをコピーするだけの交代は採用しません。DBは未反映データ・複製到達位置・主担当の停止を確認して切り替えます。2台同時の主担当化を防ぎ、予定どおり担当PCが起動しなかった場合も表示します。

DBまで交代する場合の手順

  1. 交代時に両PCを同時に起動する時間を確保。新しい外部処理を止め、入力・送信中・結果不明の一覧を保存。
  2. 最後の書込位置まで予備に到達・適用したことを確認。旧主担当への新規書込を止め、必要なファイルの版も確認。
  3. 旧主担当を停止・隔離後、次のPCを昇格して接続先を変更。ログイン・読取・安全な保存を確認してワーカーを再開。
  4. 同時起動できなかった場合は検証済みバックアップと最終ログから復元。最終退避後の操作は端末控えと反映先を照合し、結果不明のまま再送しない。

曜日交代では、常時稼働機に比べて交代回数・起動忘れ・引継ぎ失敗・停止時間が増えます。資料作成の担当交代は比較的扱いやすく、DBまで毎回交代すると運用は複雑になります。24時間の新規受付が必要なら、Web・認証・DBを置く固定の常時稼働先を確保する案を優先します。営業時間内だけでよければ、全PC停止時間を受付時間外と明示する塾内完結案も成立します。どちらを採るかは、必要な受付時間と機器を確認して決めます。

この節は追加の設計案です。実機の曜日設定、DB交代、タスク有効化は実施していません。NASで稼働DBを共有する代案や、確認なしの自動昇格は採用しません。
